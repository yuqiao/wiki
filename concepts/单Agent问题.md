# 单Agent问题

## 概念 (Concept)

单Agent问题指使用单个大模型Agent处理复杂任务时遇到的结构性限制。这些问题不是模型能力不足导致的，而是单Agent架构本身的固有约束——就像单核CPU无法通过"更快"来解决并行计算问题一样。

核心公式：**Agent = Model + Harness**。模型只提供能力来源，Harness（系统提示词、工具调用、状态管理、约束机制）才让模型变成真正的Agent。单Agent的问题大多出在 Harness 层面。

## 价值 (Value)

理解单Agent问题的价值：
- **避免无效优化**：当你知道40%上下文阈值后，不会尝试通过"更强的模型"解决——这是架构问题
- **正确选型**：简单任务用单Agent足够，复杂任务需要多Agent架构
- **投入产出比**：P0优先级（AGENTS.md、Linter、知识仓库化）成本低、见效快

## 用法 (Usage)

### 六大问题及解法

| 问题 | 表现 | 根因 | 解法 |
|------|------|------|------|
| **上下文饱和** | 推理质量在~40%上下文时断崖下降 | 注意力稀释、信息干扰 | 分层注入、Context Resets、记忆外化 |
| **长链路失控** | 多步骤任务中途跑偏、忘记目标 | 无状态校验、熵累积 | 进度文件、检查点、独立验证层 |
| **自我纠错难** | 犯错后越改越乱、进入死循环 | 缺乏外部客观反馈 | Evaluator角色、自动化测试、CI反馈 |
| **能力边界模糊** | 不知道任务会不会失败 | 无自知之明机制 | 评估层、置信度输出、fallback机制 |
| **知识散落** | 团队知识在Slack/会议中 | Agent无法访问非仓库知识 | 知识仓库化、AGENTS.md、文档即代码 |
| **熵累积** | 代码/文档质量逐渐下降 | 生成速度 > 清理速度 | 后台清理Agent、定期垃圾回收 |

### P0/P1/P2 行动清单

**P0（立即做）**：
1. 创建 AGENTS.md（~100行目录，指向深层文档）
2. 构建自定义 Linter + 修复指令（结构化约束）
3. 把团队知识放进仓库（文档即代码）

**P1（P0后做）**：
1. 分层管理上下文（L1-L6架构）
2. 建立进度文件和功能列表
3. 给Agent端到端验证能力
4. 控制上下文利用率（不超过40%）

**P2（有余力做）**：
1. Agent专业化分工（Planner/Generator/Evaluator）
2. 定期垃圾回收（对抗熵增）
3. 可观测性集成

## 原理 (Principle)

### Harness Engineering 六层架构

| 层级 | 名称 | 解决什么问题 |
|------|------|-------------|
| L1 | 信息边界层 | Agent该知道什么、不该知道什么 |
| L2 | 工具系统层 | Agent怎么跟外部世界交互 |
| L3 | 执行编排层 | 多步骤任务怎么串起来 |
| L4 | 记忆与状态层 | 长任务中间结果怎么管 |
| L5 | 评估与观测层 | Agent怎么知道自己做对了没有 |
| L6 | 约束、校验与恢复层 | 出错了怎么办 |

### 40% 阈值现象

Dex Horthy 观察：168K token上下文窗口，用到~40%时Agent输出质量开始明显下降。

| 区间 | 表现 |
|------|------|
| Smart Zone (0-40%) | 推理聚焦、工具调用准确、代码质量高 |
| Dumb Zone (>40%) | 幻觉增多、兜圈子、格式混乱、低质量代码 |

**原因**：模型注意力机制在长上下文中稀释，信息干扰增大。

### 瓶颈不在模型

Can.ac 实验：同一个模型，只换文件编辑接口调用方式，编码基准分数从6.7%跳到68.3%。模型没变，变的是Harness。

> "If it cannot be enforced mechanically, agents will deviate." — OpenAI

## 心法 (Best Practices)

### 何时用单Agent

**适合**：
- 任务链路短（<10步）
- 上下文需求小（<40%窗口）
- 有明确成功标准
- 独立任务，无依赖

**不适合**：
- 复杂多步骤任务
- 需要专业知识分工
- 长时间运行
- 需要自我验证

### 多Agent架构模式

当单Agent不够时，进化到多Agent：

```
Planner（规划者）→ Generator（执行者）⇄ Evaluator（评估者）
```

- **Planner**：把模糊需求展开成规格
- **Generator**：按功能做Sprint
- **Evaluator**：用Playwright等工具实际运行打分

### Context Resets 技术

当Agent上下文接近饱和：
1. 提取当前状态、已完成工作、待办事项
2. 启动全新"干净"Agent
3. 交接结构化文档
4. 新Agent从干净状态继续

### 熵对抗原则

熵不会自己消失，必须主动对抗：
- 后台Agent定期扫描架构违规、文档不一致、冗余代码
- 清理速度 ≥ 生成速度
- 每次Agent犯错，工程化一个解决方案让它永不重犯
